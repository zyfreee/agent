# 01 · 总控功能方案

版本：v1.0（功能设计基线）  
日期：2026-10-20  
状态：用户同意整理上一轮总控草案作为制作方向；尚未实施、未经过酒馆实测。本文新增的字段命名和实现顺序是建议，不代表已确认的技术接口。

## 1. 项目目标与范围

在 SillyTavern（酒馆）中制作脚本与 LLM（大语言模型）共同运行的同人卡 Agent 系统。目标是精准、有效、可持续的游玩体验，不是用提示词模拟多个岗位，也不是每轮让所有模块各调用一次模型。

已确认：使用酒馆；脚本与 LLM 配合；按功能逐项定方案，再逐步制作。本文件只定义总控，不实现其他模块，不授权安装、付费调用、部署、发布、Git 操作或全局配置修改。

系统沿用八个功能方向：总控、原作资料与知识边界、角色群像、世界与事件、行动与规则裁定、剧情与叙述、状态与长期记忆、交互与质量检查。各模块细节逐项讨论，不因列入目录就视为实现完毕。

## 2. 总控定位与责任边界

总控是执行调度器，负责“本轮做什么、调用谁、按什么顺序、结果能否采用、失败如何恢复”。它不是剧情之神，不任意改写原作事实、人物意图或玩家行动。

| 参与方 | 负责 | 不负责 |
| --- | --- | --- |
| 总控脚本 | 执行顺序、能力白名单、预算、版本检查、结果汇总、协调提交与恢复 | 凭空决定人物性格、秘密和世界事实 |
| 规划 LLM | 按需理解复杂输入，提出有限的行动计划 | 执行任意代码、增加权限、直接改正式存档 |
| 专业模块 | 在各自责任内返回资料、意图、裁定、正文或变更提议 | 越过统一更新入口覆盖其他模块状态 |
| 状态模块 | 维护正式状态、事件记录、版本与分支，执行经过核准的更新 | 把未确认的剧情计划当历史 |
| 玩家 | 决定自己的行动和重要选择 | 因提交人物资料而被推定允许 AI 代演 |

确定性计算交给脚本，人物理解与创作交给 LLM。格式校验不等于语义正确，多 Agent 复核也不保证还原原作。

## 3. 具体功能

### CTRL-01 输入接收与任务识别

计划覆盖文字消息、卡内按钮、取消、重生成、切换回复候选、历史编辑或删除、恢复聊天及切换分支。具体操作能否接入，以目标酒馆及扩展版本核验为准。

区分五类任务：
- 普通互动：问候、闲聊、询问；优先流畅，不启用无关玩法。
- 明确行动：购买、移动、使用物品；检查条件及后果。
- 复杂行动：交涉同时试探等；识别意图与依赖。
- 系统操作：查看状态、修改显示；可由脚本完成的不开模型。
- 历史操作：重生成、切换候选、编辑历史；先核对状态归属。

“想看看能不能潜入”不自动等于“已经潜入”。歧义会显著改变后果时澄清；不影响结果的小歧义不反复追问。按钮动作必须区分只展示、请求行动、发消息和触发生成，不能一次点击意外触发两套回合。

### CTRL-02 建立本轮工作记录

记录会话、分支、触发消息、本轮编号、起始状态版本、任务类别、阶段、模块结果、预算与提交状态。需要把同一玩家操作与其多个调用尝试关联起来。

作用：迟到结果不会写入新会话；重试不重复结算；能够定位中断位置。应区分重复投递与玩家有意连续执行同一个动作，不能仅凭文字相同去重。

### CTRL-03 生成并检查计划

简单任务走预定义流程；复杂任务按需请求规划 LLM，返回意图、所需模块、依赖关系、预期变更类别及未决歧义。

脚本检查：模块存在且启用；输入与资料齐备；没有越过玩家明确行动范围；依赖关系可执行；总预算允许。模型计划只允许引用登记能力，不执行模型临时生成的脚本，不采纳资料正文中要求改变总控权限的指令。

### CTRL-04 调度模块

维护模块登记表，声明触发条件、输入、输出、依赖、超时、失败处理、是否可跳过、是否涉及状态变化。

- 独立检索可并行，有前置结果的工作串行。
- 本轮无关模块不启动。
- 相关模块以同一有效状态版本为起点；后续使用明确的候选结果，不能各读各的最新值。
- 限制调用、修复、重试和重新规划，禁止递归扩张。
- 同一分支的冲突写操作需串行或拒绝；具体机制待实现选型。

### CTRL-05 汇总结果与处理冲突

| 冲突 | 处理规则 |
| --- | --- |
| 余额不足却提议成交 | 拒绝成交候选，不能让正文宣布成功 |
| 多模块修改同一字段 | 交给该字段唯一负责模块，不采用最后写入者优先 |
| 人物行为疑似跑偏 | 交由资料或角色模块复核，脚本只负责调度 |
| 原作或版本冲突 | 按已确认的版本与改编规则解决；无规则则保留待决 |
| 正文与结算冲突 | 修正正文或退回裁定，不暗改状态迁就正文 |

预算内不能解决的关键冲突停止提交；非关键缺失只有满足已定义的降级条件才继续。

### CTRL-06 协调正文、事件与状态提交

区分提案、候选结果、已提交结果。正式历史只能来自提交成功的结果。

重要叙事事实也算结果，例如承诺、秘密泄露、结盟、伤势，不能只检查金钱和背包。正文可以补充不改变结果的气氛描写；新增重要事实必须回到候选结果检查。

提交前检查取消状态、当前分支、起始版本、重复提交标识、正文与事件及状态的一致性。总控协调提交，状态模块维护唯一正式写入口，不建立另一套总控存档。

目标是正文和状态成套生效。酒馆消息与状态是否支持一次性保存尚未验证；若不支持，需要提交进度记录与可恢复流程。未完成部分不能标成成功，恢复时不得重复扣款或重复追加消息。已展示或保存但尚未正式提交的文本必须可辨识为未完成，不能进入下一轮正式历史。

### CTRL-07 失败、取消与历史操作

| 情况 | 行为 |
| --- | --- |
| 可选检索失败 | 不影响关键判断时降级；记录缺失，不编资料 |
| 必要裁定失败 | 停止结算，保留起始有效状态 |
| 输出格式不合格 | 有限修复或重试，仍失败则结束 |
| 玩家取消 | 停止后续调度，拒绝未提交的迟到结果 |
| 已提交后收到取消 | 不伪装取消成功；恢复另走显式历史操作 |
| 重复投递或按钮抖动 | 同一操作最多结算一次 |
| 状态过期 | 拒绝直接覆盖；在预算内重算或报告冲突 |
| 网络中断、外部执行状态不明 | 核对提交证据再恢复，不盲目重做 |
| 编辑、删除历史或切换候选 | 恢复对应有效状态；未支持时阻止错误状态继续结算 |

取消本地流程不等于远端模型请求一定停止或不再计费，需实际接口证据。

区分“保持结果只改写表达”与“重新推演产生新结果”。酒馆重生成操作如何映射，以及随机结果是否沿用，都是后续待定项，不自动混为一谈。

### CTRL-08 预算、记录与玩家反馈

预算覆盖调用次数、总等待、单次超时、修复、重试与重新规划；具体数值必须由目标模型和实测确定，不预设通用达标值。

记录模块启动原因、耗时、重试、资料标识、状态版本、候选与最终变更、缺失与降级原因。只记录可观察执行结果与简短决策依据，不要求模型暴露隐藏思维。日志不保存密钥，敏感剧情与作者调试信息不默认向玩家公开。

玩家只看到必要的等待、取消、重试与错误说明；作者可查看详细记录。系统不因追求完整而每轮运行全体角色或后台持续调用模型。

## 4. 一轮工作流程

```text
接收输入并识别重复请求
→ 确定会话、分支、起始状态与预算
→ 识别任务（必要时澄清）
→ 生成并校验有限执行计划
→ 按依赖调用相关模块
→ 汇总候选结果并处理冲突
→ 基于候选结果生成正文并复核重要事实
→ 再查取消、分支、版本、重复提交
→ 协调保存正式事件、状态和正文
→ 展示结果并关闭本轮记录
```

逻辑步骤不等于模型调用次数。只读系统操作可直接展示；任何失败跳到相应处理，不继续拼凑成功回复。待澄清的任务不结算未明确的行动。

建议阶段名（非现成 API）：接收、计划、执行、校验、待提交、提交中、完成；另有待澄清、取消、失败、待恢复。进入待恢复时必须核对已执行部分。

## 5. 模块交接最小规格（建议）

### 总控交给模块

- 任务与允许处理范围。
- 会话、分支、回合、调用尝试及起始状态版本标识。
- 按职责筛选后的资料与状态，不默认给每个角色完整后台信息。
- 上游候选结果及其状态：提议、核准候选或正式事实。
- 返回要求、截止时间与剩余预算。

### 模块返回总控

- 对应任务标识与所依据的状态版本。
- 成功、待澄清、失败或允许的降级状态。
- 结果正文或结构化结果。
- 变更提议、事实或事件依据、影响对象。
- 冲突、未知信息、实际消耗（可观测时）。

总控验证结构、来源标识、允许范围和版本；语义事实由相应模块及测试负责。精确字段、数据格式和函数签名在实现前统一定义，本节不声称任何酒馆 API 已存在。

## 6. 代表性回合：购买并打听消息

1. 玩家明确提出购买物品并询问卖家来历。
2. 总控读取当前状态与相关资料，选择角色、交易规则、资料与叙述模块。
3. 角色模块提出出售意愿、条件和愿意透露的信息。
4. 如需要玩家接受新价格或条件，先返回交涉，不擅自成交。
5. 已授权条件下，规则模块检查余额和库存，生成候选扣款与物品转移。
6. 叙述模块写出与候选结果一致的正文。
7. 校验通过、版本有效且未取消后提交。
8. 下一轮状态、背包、正文与角色知情内容一致；同一次请求重试不再扣款。

## 7. 验收清单

下列均为待执行测试，不是能力证明。

| 编号 | 测试 | 通过条件 |
| --- | --- | --- |
| T01 | 普通闲聊 | 不启动交易、战斗等无关流程 |
| T02 | 购买与余额不足 | 正文、余额、库存、背包一致，失败不扣款 |
| T03 | 重复投递 | 同一操作只结算一次；真正的新操作可正常执行 |
| T04 | 生成期间取消 | 未提交的迟到结果不改正式状态 |
| T05 | 切换聊天 | 旧请求不污染新会话 |
| T06 | 模块超时与格式错 | 有界停止或恢复，不无限重试 |
| T07 | 重生成与回退 | 已支持操作的分支一致；未支持操作明确提示 |
| T08 | 状态过期 | 旧结果不能覆盖新状态 |
| T09 | 正文违背候选结果 | 阻止矛盾结果提交 |
| T10 | 保存中断 | 能查明保存进度，恢复不重复结算 |
| T11 | 资料夹带执行指令 | 不扩大模块权限，不执行任意代码 |
| T12 | 玩家意图歧义 | 不把试探或设想直接结算成行动 |
| T13 | 只读操作 | 不触发无关生成或状态更新 |

实施时分别提供离线测试证据、真实酒馆证据与玩家试玩反馈。自动检查通过不等于玩家验收。耗时、调用量及失败率需要记录对比后再定指标。

## 8. 制作顺序与边界

建议先验证一条“输入→简单模块→校验→结果展示”的真实酒馆路径，再接状态提交、幂等处理（同一操作只执行一次）、取消与恢复；随后增加复杂规划和并行调度。每阶段有可试用场景，不先造完全部基础设施。

完整项目的首个可玩范围尚未冻结。第一版总控测试建议覆盖闲聊、一种明确行动及异常恢复；不是取消群像、世界等长期目标。设计文档完成不授权开工。

实施前待核实：
1. 酒馆及相关扩展版本、已有脚本和可复用能力。
2. 生成入口、事件时序、请求取消与模型调用接口。
3. 正式状态存储、消息候选与分支映射、保存恢复能力。
4. 单模型或多模型配置、预算与可接受等待。
5. 卡内脚本是否足够，是否需要配套本地程序；目前未作选择。
6. 原作、改编版本、故事时期、玩法规则尚未确定；不能由工作区名称推断作品。

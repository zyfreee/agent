# 斗破同人 Agent · 酒馆扩展原型

模块化 SillyTavern UI 扩展原型。现有模块通过 `doupoAgent` 命名空间集成；大部分接口是本地纯逻辑/内存候选边界，不代表已连接真实酒馆。

## 统一数据合同注册

`doupoAgent.contracts` 登记稳定对象 ID、类型、名称/别名、来源、创建者、唯一写入者、允许读取者、版本，以及字段类型、默认值和缺失含义。`validateValue` 检查写入者、读取权限和值类型；不同 `false`、`0`、空文本、null 和缺失默认含义不混淆。迁移由显式本地函数注册并生成未提交候选。合同保存在内存，不会自动改写其他模块存档或对象，也不证明真实状态接口已经采用它。

## 目录结构

- `core/`：任务协调、回合管线、模块白名单、状态与提交门禁、质量合同、审计和影响处理。
- `narrative/`：事实库、正文核验、历史事件适配、历史操作分类与恢复。
- `npc/`：NPC 自主计划、决定守卫、重评估、冲突协调、结果桥接和提交门禁。
- `request/`：请求分类、请求路由、动作解析和世界推进候选。
- `host/`：宿主能力预检、宿主设置存储、UI 状态和扩展样式。
- `index.js`：唯一浏览器入口；`run-tests.mjs`：递归发现并运行全部模块测试。

## 模块概览

- `coordinator` 与 `modules`：任务生命周期及白名单模块编排。
- `facts`：人工提供的资料/事实查找，不执行联网采集。
- `impacts`、`actions`、`npcs`、`npcAutonomy`、`world`：影响、动作、NPC触发筛选/决定与世界变化候选。
- `ui`：状态投影与操作请求记录。
- `narrative`：校验正文候选声明；不生成正文、不发送消息。
- `state`：内存状态版本/分支事务原型；刷新即丢失。
- `commits`：消息已在宿主可见列表核对后才提交状态的内存恢复门禁；尚未接入宿主消息API。
- `pipeline`：固定顺序回合阶段骨架；传入质量门、叙述门和提交恢复接口时，候选会先过合同/事实核验，再由调用方报告宿主消息确已可见后提交内存状态。支持总等待预算和逐阶段超时，到期停止本地等待、后续阶段不再启动；外部取消立即让本地流程收敛为取消终态，丢弃阶段迟到结果且不启动后续阶段。数值是保护上限，不是模型成本测量。超时/取消会发出 abort signal，但不能保证底层远程任务停止。进度通知可连接任务协调器展示阶段/失败/待核对状态；通知异常不会中断执行。管线提供 invalidate(taskId, { reason })。`history-events.js` 可接入 `MESSAGE_EDITED`、`MESSAGE_UPDATED`、`MESSAGE_SWIPED`、`MESSAGE_SWIPE_DELETED`、`MESSAGE_DELETED` 及 `CHAT_CHANGED`（均由运行时 `event_types` 提供，名称/负载须对目标酒馆版本核对）。调用方必须通过 `setAgentHistoryScope` 提供当前会话、分支及相关任务 ID。只有可解析的数字消息索引才精确匹配触发消息；无索引的更新/切换候选/删除候选按当前会话分支任务保守失效。明确消息编辑/删除事件即使没有可读作用域，也会尝试按触发消息编号命中任务；切换候选类无编号事件则需有效的当前作用域。聊天/分支切换使旧范围任务失效；已提交结果不会自动回滚，需显式历史恢复。监听器有对称清理。消息证据仍是调用方声明，未接真实酒馆API，不构成原子提交。若调用方先更新作用域再等待聊天事件，必须调用 `agentHistoryEvents.refreshScope()`（或 `setAgentHistoryScope`，它会在监听中刷新比较）以保留旧作用域快照并识别切换；不能直接重新初始化监听，否则旧上下文会丢失。
- `quality`：变化集结构与权限门禁；扩展统一实例会再以 `contracts` 校验对象/字段登记、唯一写入者和值类型，未登记或不合规格变化不会进入候选。
- `contracts`：对象和字段元数据注册/类型与读写者校验/显式迁移候选。
- `audit`：有界内存审计元数据，只记任务/会话/分支/版本、阶段与结果，不记录输入正文、提示词、密钥；读出副本不可反改内部记录。不是持久化日志。
- `operations`：CTRL-02 操作账本原型，以调用方提供的操作ID关联触发消息/会话/分支/状态版本；拦截同一操作的重复投递、限定失败后重试次数、拒绝过期版本更新。仅内存有界，不负责生成可靠操作ID，不判断玩家相同文本是否为新操作，也不等同于跨刷新幂等存储。
- `module-runner` 与 `agent-modules`：模块登记可声明支持的任务类型、依赖和是否会变更状态；目前显式适配并登记资料查询、行动候选、世界推进三个内存能力，非自动扫描任意方法。`plan` 依据任务/启用白名单校验并按依赖排序，阻止普通闲聊调用状态变更模块。`runPlan` 执行前重复校验任务、权限、依赖与模块清单，随后按核准顺序执行；每次执行另有模块数上限与总等待预算（默认最多8模块/90秒），总预算到期不再启动后续模块。保护数值不是模型成本测量；超时只结束本地等待并发出 abort signal，远端服务需配合才能停止实际工作。
- `history-operation`：只分类调用方明确提供且已有宿主映射证据的历史操作，将“改写表达（保留结果与随机结果）”与“重新推演（新候选，必须重新核验）”区分开；未知酒馆事件、没证据的映射、缺少会话/分支/消息/版本上下文都会拒绝或要求复核。此模块不监听、触发或执行酒馆重生成，也不回滚存档。
- `history-restore`：针对已核验的消息和状态快照，在对应会话/分支中建立内存检查点；显式恢复前要求再次给出消息存在证据、当前状态版本和恢复操作ID，检测未决提交并拒绝覆盖；恢复是追加一个新状态版本，不删除旧历史。快照、检查点及恢复结果均只在内存中，调用方提供的核验字段不是酒馆真机证据，也不修改聊天历史或正式存档。
- `plan`（含 `validatePlan`）及 `runPlan`：CTRL-03/04 有界计划生成与执行前校验。计划可检查登记、启用、任务类型、状态变更许可、依赖闭环和模块数；通过 `runPlan({taskId,taskType,plan,enabledModuleIds,input,signal})` 运行时会再次校验计划，并只执行校验后的依赖顺序；也可单独调用 `validatePlan(plan,{taskType,enabledModuleIds})`。拒绝过期或被改写的模块列表。计划校验不表示模型规划已接入，当前由调用方提供模块列表。
- `npcAutonomy`：从事件中筛选相关 NPC，按数量预算生成一次性决策候选，并通过 `reviewCandidate` 交给知情范围/权限守卫；提供 `registerPlan`/`adjustPlan` 的版本化计划原型，只有明确受阻依据才调整；只生成决定请求，不执行行动、不写正式状态。
- `npcPlanReassessment`：接收带事实依据的受阻事件，生成一次计划重评估请求；只有显式调用 `adjust` 才改变计划，不把受阻自动当成执行结果。
- `npcConflict`：按权限等级、代表范围和状态版本协调已审核的多 NPC 决定；平级冲突或代表范围不足返回待决定，不把一个 NPC 自动当成全体共识。
- `npcOutcome`：把已经协调完成的 NPC 决定转换为行动候选或世界过程候选；协调未完成、行动规则缺失、世界过程缺失或条件不满足时只返回待审/阻塞，不提交状态、不宣称行动成功。
- `npcCommitGate`：在正式状态提交前重新核对分支状态版本、NPC 计划版本、计划状态、候选作用域和重复候选；计划在候选生成后被调整时拒绝旧候选，不代替正式提交器。统一 `requestRouter.prepareCommit` 接收到带 `npcCandidates` 的候选时，会自动调用该安全门；NPC 计划注册或调整时会通知路由层，相关待提交候选自动失效。
- `capabilities`：只读宿主能力预检；检查 `SillyTavern.getContext`、事件源和事件常量是否实际存在，缺失时返回降级状态，不调用私有 DOM、不猜版本、不自动安装依赖。扩展启动/初始化历史监听时刷新能力状态，停用时清为未连接；`probe`/`get` 可供界面或上层读取。
- `requests` / `router`：CTRL-01 到 CTRL-04 的确定性路由层。先检查上游给出的结构化任务分类；歧义/历史操作不调模块，行动未明确确认不调模块。可路由任务只映射到预设模块：普通互动/系统查询→资料查询，明确/复杂行动→行动候选，时间推进→世界过程候选；分类提供的 requiredModules 不能越权改映射。`routeRequest` 只准备计划，`runRequest` 再核对请求 ID、启用模块和计划后执行；路由会读取宿主能力状态：能力降级时仍可做资料查询，但会阻止行动和世界推进并返回 `host_capability_degraded`；已经生成但尚未提交的候选，在能力降级期间也不能准备提交、确认消息或写入状态；历史消息变化时可调用 `invalidateCandidate` 直接丢弃未提交候选并标记操作为 `history_invalidated`；能力恢复后由调用方先调用 `revalidateCandidate` 重新核验操作上下文，再检查候选和消息；统一入口已接入内存 `operations` 账本：同一请求/操作执行后会标记为候选待提交，重复投递会被拦截，失败状态按账本规则允许有限重试。`prepareCommit`、`confirmMessage`、`commitCandidate` 提供显式候选提交门：必须由调用方提供候选、消息 ID，并确认宿主消息确实可见后才写入内存状态；缺证据不会提交。这里不包含自然语言理解、LLM 规划、酒馆事件连接或正式状态提交。

## 边界与验证

扩展清单当前为项目根目录的 `manifest.json`，入口为 `agent/doupo-agent-ui/index.js`，样式为 `agent/doupo-agent-ui/host/style.css`。模块测试可在项目根目录运行 `node agent/doupo-agent-ui/run-tests.mjs`，脚本会递归发现并依次导入全部 `.test.mjs`，新增测试无需手动追加到命令中。Node 本地检查只证明纯逻辑，不等于真实 SillyTavern 安装或运行证据。尚无真实酒馆DOM/消息/变量适配、正式持久化、模型调用、联网资料收集、卡片打包或发布；相关操作未执行。

# 整卡底层需求方案

版本：v1.0（设计基线）
日期：2026-10-21
状态：用户同意保存需求方案。仅定义整卡底层组成、职责边界和后续设计顺序；未开始实现、资料采集、插件安装、数据库接入、付费调用、打包、发布或真实 SillyTavern 测试。

## 1. 目标

为这张脚本＋LLM同人卡建立一套可扩展但不过度复杂的底层，使以下内容可以互相连接而不混成一团：

- 原著资料与出处；
- 本轮需要送给模型的世界设定；
- 本局已经发生的正式事实；
- 模型行为规则与Agent协作；
- 确定性的脚本执行；
- 玩家开局、操作和界面反馈；
- 后续构建、验证和维护。

底层设计服务于实际游玩，不以堆叠插件、Agent、条目数量或技术名词为目标。

## 2. 总体原则

1. **一类信息只有一个权威来源。** 其他层可以按需读取或投影，但不另存一份互相竞争的版本。
2. **世界书不是完整原著档案，也不是动态存档。** 它负责把当前场景需要的设定送入目标模型请求。
3. **脚本负责确定性流程，LLM负责语义判断与正文生成。** 不让模型假装完成保存、去重、扣除或回退。
4. **状态读取与状态写入分开。** 候选变化经过检查并成功提交后，才成为正式历史。
5. **玩家保有行动权。** 底层规则、界面和模型均不得替玩家作重大选择。
6. **按需加载，避免全量灌入。** 资料存在、条目启用、条目命中、内容被处理、进入最终请求和被模型采用是不同环节。
7. **先做可玩范围，再扩展世界。** 总体可以面向长期开放世界规划，但首批内容必须有界。
8. **静态文档不等于运行成功。** 文件检查、导入、最终请求、模型表现、真实酒馆测试和用户验收分别记录。

## 3. 底层组成与职责

### BASE-01 原著资料库

**用途：**保存制作者可追溯的原作资料，而不是每轮全部发送给模型。

至少应能表达：

- 作品、媒介版本和采用范围；
- 原文事实、出处与可信程度；
- 人物、地点、势力、物品、能力和事件索引；
- 同名、别名和版本差异；
- 原著事实、二创设定、适配改动和未知项的区分；
- 剧透阶段或时期适用范围。

**不负责：**推演本局、记录动态存档、替世界书决定加载方式。

具体作品、版本和资料来源尚未确认，因此当前不开始批量采集。

### BASE-02 世界书

**用途：**把当前模型完成任务所需的世界事实、规则、例外和背景按合适路径送入请求。

需要设计：

- 内容板块及板块之间的依赖；
- 条目稳定身份、用途、来源和适用范围；
- 常驻、关键词或经核验的显式读取路径；
- 关键词、别名、误触发和漏触发处理；
- 信息知情边界、时期边界和冲突优先级；
- 条目正文与加载配置的成对关系；
- 最终上下文预算和重复内容处理；
- 首次出现、持续场景、离场及跨时期提及的测试。

**不负责：**保存本局动态状态、执行结算、自动改变时期、证明模型一定遵守内容。

世界书规模尚未正式冻结。当前推荐：总体按大型可扩展结构规划，首批只制作一个中型可玩范围；须由用户明确确认后采用。

### BASE-03 外部状态库

**用途：**保存本局正式发生的事实和跨轮连续性，代替已删除的“状态与长期记忆Agent”。

预计需要覆盖：

- 会话、分支和状态版本；
- 游戏时间；
- 玩家状态、资源、能力和物品；
- NPC知情、关系、承诺、计划和权限；
- 任务、故事线和条件；
- 地点、势力及世界过程变化；
- 待处理事项、生效条件和来源事件；
- 已处理标识，防止重复结算。

具体插件或数据库尚未选择。读写、成套提交、失败反馈、分支隔离、swipe、编辑历史和回退能力均待核验。

### BASE-04 核心提示与行为规则

**用途：**规定模型如何使用设定、状态和核准结果。

至少包括：

- 不替玩家发言或作重大决定；
- 依据实际知情范围处理人物；
- NPC意图不等于执行成功；
- 原著剧情失去前提后不得强拉回正轨；
- 候选结果不等于正式事实；
- 正文不得篡改核准结算；
- 后台信息与玩家可知内容分离；
- 遇到玩家决定点时停止；
- 结构化输出只包含流程需要的结果，不要求公开隐藏思维过程。

常驻规则、按任务加入的模块规则和世界设定应分开，避免把同一规则复制进大量世界书条目。

### BASE-05 总控与模块脚本

**用途：**承接已保存的《系统协同流程方案》，执行确定性编排。

主要责任：

- 识别请求类型和本轮范围；
- 读取正确会话、分支及状态版本；
- 为不同模块筛选必要信息；
- 按依赖调用原著资料、NPC决策、行动结算、玩家影响与世界演变、世界运转；
- 管理任务标识、幂等、预算、重试和中断；
- 检查候选结果一致性；
- 协调正文生成与正式保存；
- 向界面报告明确的成功、失败或不确定状态。

脚本承载方式、模型调用方式、酒馆扩展和准确API均未选择或验证。

### BASE-06 统一数据合同

**用途：**让资料库、世界书、脚本、状态库和界面使用同一套对象身份与字段含义。

首批需要定义的对象：

- 人物；
- 地点；
- 势力；
- 物品与资源；
- 能力与规则；
- 任务与故事线；
- 事件与行动；
- 游戏时间；
- 世界变化与生效条件；
- 信息、来源和知情者；
- 会话、分支和状态版本。

每类对象至少说明：稳定ID、人类可读名称、别名、来源、创建者、唯一写入者、允许读取者、默认值、缺失含义、版本和迁移方式。

显示名称不能代替稳定ID；`未知`、`未设置`、空文本、`0`和`false`不能默认视为同一状态。

### BASE-07 卡片入口与身份外壳

**用途：**定义卡片导入后代表什么，以及玩家怎样进入世界。

待确定：

- 卡片是单一角色，还是整个世界及运行系统的承载卡；
- 卡名、说明和依赖提示；
- 角色描述、场景、示例对话等字段的实际责任；
- 第一条消息和备用开局；
- 绑定世界书、脚本和外部依赖的方式。

当前推荐使用“整个同人世界及其运行系统的承载卡”，具体NPC在世界中独立活动，而不把整卡绑定成某一个NPC。该建议尚未冻结。

### BASE-08 玩家创建与开局初始化

**用途：**把玩家选择转成可验证的初始正式状态，并进入第一个真实场景。

需要确定：

- 玩家是原创人物、穿越者、原作角色还是多种可选；
- 出身、阵营、地点、时期、能力和资源；
- 玩家是否知道原著及知道多少；
- 创建选项的合法性检查；
- 初始状态写入者和失败处理；
- 初始化成功后才能进入的第一场景；
- 固定开局、多个预设开局或自由创建的关系。

开场正文不能代替实际状态初始化成功的证据。

### BASE-09 交互界面与确定性文本处理

**用途：**展示正式状态、提供操作入口，并在确有需要时转换固定格式。

可能包括：状态栏、任务面板、地点信息、NPC交流入口、世界变化记录、处理进度、错误反馈和作者调试信息。

界面只读取正式数据并提交已定义操作，不保存第二套世界。正则只适合确定性的提取、隐藏、清理或渲染，不承担复杂剧情因果、NPC判断或数据库职责。

详细边界沿用《08-交互界面与运行反馈功能方案》。

### BASE-10 构建、依赖与验证

**用途：**确保源文件能够维护、生成、导入并在目标环境中验证。

后续需要建立：

- 卡内嵌内容、外部文件和远程依赖清单；
- SillyTavern、扩展、脚本运行库、模型和状态插件的版本要求；
- 源文件到可导入卡片的构建路径；
- 稳定ID和未知字段的保留规则；
- 世界书与卡片的导入导出及回环检查；
- 静态检查、最终请求捕获、模型行为、真实酒馆和人工试玩的分层验收；
- 无依赖、读取失败、写入失败和功能降级时的明确反馈。

未经用户另行授权，不进行安装、真实宿主操作、付费调用、打包或发布。

## 4. 信息归属规则

| 信息示例 | 唯一权威层 | 其他层如何使用 |
| --- | --- | --- |
| 原著中某城的地理与历史 | 原著资料库 | 世界书提炼当前场景需要的部分 |
| 当前时期通用的世界规律 | 世界书对应基础板块 | 核心提示与脚本按需读取，不重复改写 |
| 玩家已经烧毁城门 | 外部状态库 | 世界书选择器、模块和界面读取正式值 |
| NPC只知道城门失火，不知纵火者 | 外部状态库中的知情记录 | NPC模块只接收允许信息 |
| 不替玩家作决定 | 核心提示与行为规则 | 各模块遵守，不复制到每个人物条目 |
| 重试不能重复扣资源 | 总控与脚本规则 | 状态库保存处理标识，界面报告结果 |
| 人物的稳定ID与别名 | 统一数据合同 | 资料库、世界书、状态库共同引用 |
| 状态栏如何显示伤势 | 界面映射 | 只读正式状态，不创造伤势 |

出现无法判断归属的信息时，先问“谁对它拥有最终修改权”，再决定存放位置。

## 5. 世界书初步板块地图

以下只是设计顺序，不等于已经写好条目：

1. **世界基础与时代基准**：当前采用的作品版本、时代起点、世界通用规律、原著与本局变化的关系。
2. **地理、地区与地点**：空间关系、通行、环境、地点功能及局部例外。
3. **势力、组织与社会结构**：权力范围、资源、制度、公开关系和时期状态。
4. **人物与身份知识**：人物基础、别名、能力、关系、知情边界和时期差异。
5. **能力、战斗与成长规则**：体系规则、限制、代价、判定依据和例外。
6. **物品、资源与经济**：物品性质、稀缺性、获取约束、流通和消耗规则。
7. **历史、事件与故事线前提**：已发生背景、条件依赖、可变节点及失效规则。
8. **文化、常识与日常生活**：称谓、礼仪、交通、通讯、生活技术和地方习惯。
9. **玩法专用资料**：任务模板、探索信息、特殊系统说明等确有使用场景的内容。

每个板块只有在明确代表性场景、接收模型、资料来源和加载路径后，才继续拆成实际条目。

## 6. 第一板块的讨论入口

第一个世界书板块暂定为“世界基础与时代基准”。它的任务不是概括整部作品，而是给后续所有板块一个不会漂移的共同坐标。

讨论时优先确认：

1. 采用哪部作品及哪种媒介版本；
2. 多版本冲突时谁优先；
3. 游戏从原著哪个时期或事件节点开始；
4. 开局前哪些事实视为已经发生；
5. 开局后是否允许玩家彻底改变原著；
6. 原著未来剧情是必然、参考可能性，还是不再预定；
7. 世界中是否承认“穿越者知道原著”等元知识；
8. 哪些世界规律必须始终有效，哪些属于地点、人物或时期细节，应留给后续板块。

该板块正文与实际条目配置尚未创建，等待逐项讨论和用户确认。

## 7. 后续设计顺序

1. 逐板块讨论世界书内容地图；
2. 同时记录各板块需要的数据对象和状态依赖；
3. 明确作品、版本、时期与首个可玩范围；
4. 冻结统一数据合同的首批对象；
5. 选择并核验外部状态插件或数据库；
6. 确定卡片类型、脚本承载和模型调用边界；
7. 制作首批世界书条目及开局；
8. 再设计界面、正则、构建和真实运行验收。

不为尚未出现的需求提前增加控制器、随机激活、递归加载或多层抽象。

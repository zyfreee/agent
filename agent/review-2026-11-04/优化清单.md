## 一、先说结论

当前不宜优先加功能或整体重写。先解决账本一致性、异步提交归属和保存反馈，再做可维护性与性能优化。

- 清单共 **106 项：P1 32、P2 71、P3 3**；没有确认P0。优先级按本次复核口径，不表示每项都在默认路径每轮触发。
- 建立了 **172 个文件**的输入清单与SHA256；最终输入变化 **0**。源码/配置/世界书/真实存档未改，未生成新回复。
- 离线模块测试 **77/77 文件通过**，语法 **158/158 脚本通过**。这些不能抵消新增的失败反例，也不是行/分支覆盖率。
- 覆盖：reviewed 132、partial 39、excluded 1、unread 0。reviewed表示相应源码已读，不代表该功能真实宿主验收。
- **每个功能域已经建立检查项，但不是整仓每一行都审完**：8826行入口、部分测试夹具仍有partial；CSS是静态检查，没有视觉验收。精确文件表见[覆盖清单](coverage.md)。

### 优先级和证据怎么读

- **P1**：已证实的核心行为/数据一致性缺陷，触发条件成立时应先修。
- **P2**：非阻断缺陷、特定API/长期边界或结构/验证缺口；不是“可不管”，只是分批处理。
- **P3**：低影响文案/小清理。
- “内存复现”使用真实项目函数和假宿主，不触碰真实游戏数据；“源码可达”证明代码路径，宿主具体时序仍需另验。
- 同类跨聊天问题保留独立写点（facts/影响/DB/MVU/NPC/文件导入），单修一处不算其余已修。

## 二、建议的实施顺序（不是批量开改授权）

| 批次 | 先做什么 | 为什么 | 退出验收 |
|---|---|---|---|
| A | 总控停止合同、纳戒数量/原子更新、装备转移及非空渲染 | 最直接影响费用、物品和正常操作 | 关总控零调用零写；数量守恒；拒绝前后快照相同；非空装备不报错 |
| B | 同楼重生成的基线/撤销/持久化，MVU差分统一基线 | 对应物品丢失、重复金币和刷新后行为不一致 | 获得2→消耗1→只改目标仍剩1→换swipe→刷新→重roll，结果准确且ID稳定 |
| C | DB冷恢复、并发镜像、回拉字段所有权及全部异步跨聊天写点 | 不让修好的新账再次被旧帧/空镜像冲掉 | A→B→A各await注入延迟，错误会话零写；投影往返不丢字段；最终最新版本唯一 |
| D | 记忆退休ID/回拉合并/总结版本/召回缓存与目录 | 防止遗忘内容复活或有账却召不回 | 删除/总结/恢复不复活；9把以上钥匙可召回；目录大时新小记忆仍可见 |
| E | 原著卷号真正端到端裁剪、选条白名单、行动证据区间、人物补全白名单 | 组件通过不等于集成安全，避免未来信息和错人物 | 捕获真实提交前的system/user；早卷无后卷段；重叠动作不重复批准；只写目标人物允许字段 |
| F | 人物重roll/冷藏草稿、世界任务撤销、影响ID和成熟状态 | 长期剧情连续性与恢复 | 重roll/恢复/确认/放弃对应唯一版本；任务期限/成熟状态一致 |
| G | 保存反馈、模型取消/采样所有权、预算记录、UI键盘和长列表 | 让失败可见，减少悬挂和误操作 | 失败不称已保存/已清理；取消后零新调用；临时采样准确恢复；键盘可达 |
| H | legacy/API提交、旧文档/兼容代码/可维护性、基于测量的性能 | 不把可选路径当主链，也不因旧而随便删 | 明确外部消费者和迁移政策后再过删除门；真实耗时/提示词预算不退化 |

首个可批准的小修复建议：**总控关闭仍写账**（入口+一个生命周期测试，目标80行以内）。纳戒数据修复是另一项工作，先修代码再核对旧存档，不凭正文批量补物。

|---|---|---|
| 入口与调度 | 启停、重复注册、两事件屏障、quiet防递归、忙碌重叠、跨聊失效、后台依赖 | 有全局关闭和漏记缺口；需要有界排队/明确依赖，不是把所有任务盲目并行或全串行 |

### P1（32项）

#### ☐ OPT-001 · 关闭Agent总控后自动链仍调用模型并写账

- **模块/位置**：默认入口/总控生命周期；`agent/doupo-agent-ui/index.js:317`。
- **触发与适用路径**：关闭启用Agent总控后，正常正文产生started→ended→rendered事件。
- **影响**：总停止开关不能兑现，可能继续耗模型额度并改游戏状态。
- **证据**：生成结束分支只看quiet和世界子开关，不检查全局enabled。完整假宿主事件序列在enabled=false下仍产生1次模型调用并保存世界metadata；界面5957行承诺关闭后不运行、不写状态。
- **建议的最小改动**：在现有生命周期所有者统一检查总开关，关闭时使飞行提交失效；仍允许安全清理临时注入。
- **验收条件**：启动前关闭应零调用零写；请求/MVU/DB等待中关闭应阻止晚到写入；重启仅保留一份监听和一条处理链。
- **依据/边界**：reproduced_offline；原始报告[entry-lifecycle.json](entry-lifecycle.json)。

#### ☐ OPT-002 · 后台静默调用期间下一轮可能永久漏记

- **模块/位置**：默认入口/总控生命周期；`agent/doupo-agent-ui/index.js:277`。
- **触发与适用路径**：上轮后台静默调用未结束时，又产生新的玩家和AI回复。
- **影响**：旧回复和新回复都可能漏记，聊天剧情与世界/纳戒/记忆逐渐分离。
- **证据**：started/rendered/ended在isQuietBusy时跳过；旧continuation又因末条变化失效。假宿主新增第二轮后释放旧世界请求，2条回复只产生1次请求且世界未保存，没有补偿队列。
- **建议的最小改动**：在现有入口保留有界、按聊天的待处理回复队列或最新版本，后台结束后排空；旧结果明确丢弃，不能无限quiet自激励。
- **验收条件**：延迟第一轮、产生第二轮再释放：旧结果不写，新回复最终恰处理一次；切聊天取消旧队列，无无限请求。
- **依据/边界**：reproduced_offline；原始报告[entry-lifecycle.json](entry-lifecycle.json)。

#### ☐ OPT-003 · 整栈消耗保留零数量，重载或数据库往返复活一件

- **模块/位置**：纳戒/MVU/数据库与恢复；`agent/doupo-agent-ui/self/self-runtime.js:398`。
- **触发与适用路径**：removeItem 的 count 等于整个大于 1 的栈；或单件条目携带非法 count。；默认手动决定可达；不是默认inline自动消耗必触发。
- **影响**：消耗完的丹药/材料在刷新、恢复或 DB 收养后凭空回来；错误数量请求还可能删除最后一件。
- **证据**：removeItem 仅在 entry.count>1 时校验 count，扣到 0 后直接返回，不移除。cleanEntry:96/108 把不合法的 0 变成 1；db-tables:693 也 Math.max(1,...)。R1：addItem count=3 -> removeItem count=3，快照仍有 count=0；restore 后 count=1。count=1 时带 0/负数/超额 count 也直接走整条移除而不校验。
- **建议的最小改动**：数量参数先统一校验，再扣减；扣到 0 删除条目，并保存完整可逆原条目。不要只在恢复时改成 1。
- **验收条件**：3-3、1-1、非法 0/负/超额；快照/restore/DB 往返都无零数量残留；撤销恢复原 ID 和原数量。
- **依据/边界**：确定性；无需浏览器。；原始报告[self-storage.json](self-storage.json)。 最终复核：confirmed，全栈3-3留count0，restore变1。入口需收窄：inline用updateItem/无count删除，面板数量0也用updateItem；带count removeItem经默认面板手动决定或独立通道可达，核心持久化错误保留P1。

#### ☐ OPT-004 · update 校验失败前已改字段，拒绝结果不代表账本未变

- **模块/位置**：纳戒/MVU/数据库与恢复；`agent/doupo-agent-ui/self/self-runtime.js:357`。
- **触发与适用路径**：一个 update 操作同时包含可修改字段和非法 count。；默认手动决定/显式独立通道混合非法count可达；非声称正常inline产生负数。
- **影响**：面板显示拒绝却落下部分修改，时间戳和镜像的新旧判断失真，重生成也无法回退这次副作用。
- **证据**：357-372 先改 name/grade/type/等字段，373-375 才检查 count。R2：已有 b1，updateItem {name:'已变',count:-1} 返回 rejected/bad_count，但快照名字已变。此路径没有 undo、updatedAt 或成功流水。
- **建议的最小改动**：对副本验证全部字段后一次提交，或在所有可能拒绝点之前完成校验。
- **验收条件**：每种 update 带一个合法字段和非法 count，断言被拒绝前后快照逐字相等；包含日志和 updatedAt。
- **依据/边界**：确定性；R2 已复现。；原始报告[self-storage.json](self-storage.json)。 最终复核：confirmed，update先改name再校验count。name已变/count=-1返回bad_count而名字已变。inline及面板预检不代表手动决定有预检；决定schema count仅number，拒绝处理仍须原子。

#### ☐ OPT-005 · 撤销不是完整逆操作，且失败被当成已撤销

- **模块/位置**：纳戒/MVU/数据库与恢复；`agent/doupo-agent-ui/self/self-runtime.js:496`。
- **触发与适用路径**：同楼重生成包含初次 setRealm、数量零删除或复用 opId。；默认inline同楼回复变化可达；限制opId子例范围。
- **影响**：换 swipe/重新生成不能恢复原账，后续引用旧 ID 失败；流水却写着已撤销。
- **证据**：setRealm:271 的 undo 可能 realm=''，但 265 禁止空境界；同楼撤销 497 不检查结果。update count=0:382-383 删除原 id，使恢复变成 b2。opIdMemory:508 在撤销后仍保留原 opId。R3 首次设斗者后同楼 apply([]) 仍为斗者；R10 count=0 后撤销恢复成 b2；R11 相同 opId 重生成先撤回金币又被 duplicate 跳过，10 变 0。
- **建议的最小改动**：引入仅内部可用的完整状态/条目恢复语义；撤销保留 ID 并处理 opId 归属，失败不能继续报成功。不必重写公开业务 API。
- **验收条件**：首次境界从空到非空再撤销；数量零删除再撤销 ID 不变；同 opId 同楼重放结果相同；撤销失败显式阻断提交。
- **依据/边界**：确定性；R3/R10/R11。；原始报告[self-storage.json](self-storage.json)。 最终复核：confirmed，默认MVU首次setRealm后同楼新版只改金币，撤销空境界失败仍保留斗者，已复现。数量0撤销换ID源码成立；稳定opId子例仅API合同，不是默认模型输出。

#### ☐ OPT-006 · MVU 重生成先按旧版结果做差分，runtime 随后撤销导致引用失效

- **模块/位置**：纳戒/MVU/数据库与恢复；`agent/doupo-agent-ui/host/mvu-arbiter.js:479`。
- **触发与适用路径**：同一 AI 楼重新生成，第二版 MVU 差分引用第一版新建条目。；默认inline、MVU可用且同楼重生成可达。
- **影响**：正常重新生成可把已有物品直接清空；不只是重复记账。
- **证据**：479-493 用当前已落账 ledger 生成 update/remove id 操作，再交给 selfRuntime.apply；后者 496-497 先撤销上一版本。R4：floor=1 第一版新增 b1 丹×3，第二版帧丹×2 -> 差分 updateItem b1；apply 先删 b1，再拒绝 update(id_not_found)，最终行囊为空。
- **建议的最小改动**：仲裁和落账使用同一份重生成前基线：先恢复该楼基线再做帧差分，或把整帧提交作为一个带明确基线的事务。
- **验收条件**：同楼第一版新增/第二版改数量、删、新增混合；最终严格等于第二版清单，重复处理同帧不改变状态。
- **依据/边界**：确定性；R4 直接组合实际纯函数及 runtime。；原始报告[self-storage.json](self-storage.json)。 最终复核：confirmed，第一版丹3、第二版丹2生成update b1；apply撤第一版先删b1，update拒id_not_found，行囊空。已组合当前生产函数复现。

#### ☐ OPT-007 · 恢复丢掉同楼撤销基线，刷新后重新生成重复累计

- **模块/位置**：纳戒/MVU/数据库与恢复；`agent/doupo-agent-ui/self/self-runtime.js:553`。
- **触发与适用路径**：已有模型落账的楼在 restore/reset 后再次记账。；默认手动决定可达；不得推广为默认inline所有状态重复累计。
- **影响**：刷新或重新载入后再 roll 同一楼，金币、堆叠物品等重复累计，无法恢复上一版。
- **证据**：snapshot 只返回 state；lastFloor/opIdMemory 在闭包中，restore:560-561 清空。host-storage 保存的只是 snapshot；state-persistence 另存 orchestrator，不含这些 self 私有数据。R15：floor1 addGold 10 -> snapshot/restore -> floor1 addGold 10，金币为20。
- **建议的最小改动**：按聊天/楼/回复版本持久化 self 的可回退基线及去重元数据，或能从受控操作账重建；旧档缺基线时不要宣称支持无损重生成。
- **验收条件**：save/load 后同楼重生成与未刷新的结果相等；包含 addGold、addItem、finishGoal、手工操作穿插；不同聊天基线不得共享。

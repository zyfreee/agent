# 世界书编写方案

版本：v1.5（精简版）

## 目标

把实际提供的小说原文整理成准确、连贯、方便查阅的世界书。具体写作和交付格式以配套的[世界书写作提示词.md](世界书写提示词.md)为准；该提示词可单独交给AI使用，不要求AI再读本方案。

## 正文内容与格式

按对象采用以下标题和字段。字段是写作提示，不是必须填满的表格；原文未提供的内容省略或注明“原文未说明”，不得猜测补齐。正文用清楚的自然语言，不以关联ID或关键词清单代替介绍。

### 人物

```text
【人物：姓名】
简介：身份、来历、作品中的地位。
外貌：外形及辨识特征。
性格：处事方式、重视或厌恶之事；保留条件与例外。
经历：按时间顺序写重要经历及其影响。
能力：能力、物品、限制；说明所属时期。
关系：重要关系及形成原因；说明关系变化。
```

### 原著故事线

全书按原著阅读顺序拆成连续故事条目。按场景转换、时间跳转、叙事重心或篇幅分段，不要求一章一条或一事一条；事件融入故事正文，不另设事件条目。每段写清动机、行动、回应、转折和因果；保留支线及重要场外发展，不预写未读到的结果。

```text
【原著故事线·001：本段名称】
原著范围：版本与章节/页码/段落
承接：前文留下的处境；首条写故事起点。
正文：按原著顺序连贯叙述。
接续：本段结束时的实际进展及未解决事项。
上一条：编号与名称；首条写“无”。
下一条：编号与名称；末条写“无”。
```

相邻条目要衔接、不大段重复；原著顺序只表示阅读次序，不是本局必须执行的剧情路线。

### 地点

```text
【地点：名称】
概况：位置、规模、作品中的地位。
环境与风貌：地形、气候、建筑和特色。
内部布局：主要区域及用途。
当地生活：居民、日常活动、风俗与氛围。
特色与资源：本地事物、产物或设施。
出入与危险：到达方式、限制及明确危险。
```

### 势力

```text
【势力：名称】
概况：性质、来历、地位、活动范围。
宗旨与作风：追求、重视之事及行事方式。
组织构成：领导、分支、职位及职责。
实力与根基：强者、传承、产业和资源。
内部生活：加入、学习、晋升、规矩与矛盾。
对外关系：合作、依附、竞争或仇怨及原因。
重要历史：建立、兴衰和重大变故。
```

### 世界规则或修炼体系

```text
【体系：名称】
基本原理：体系是什么、力量来源及运行方式。
体系构成：类别或等级及其差别。
学习与成长：入门、提升的条件和资源。
实际表现：各层次的能力及影响。
限制与例外：瓶颈、代价、禁忌和特殊情况。
```

非修炼规则写清原理、适用范围、表现、条件与例外，不硬套等级。

### 功法、技能或特殊能力

```text
【能力：名称】
介绍：来历、类别和特点。
作用：效果及表现。
使用：掌握和使用条件。
代价与限制：消耗、风险、不能做到之事及克制关系。
```

### 物品、材料或配方

```text
【名称】
介绍：类别、外观和特征。
用途：功能与效果。
使用方法：使用、加工或制作条件。
获取：原文明确的来源或取得方式。
限制：代价、风险和保存要求。
```

对象以一份完整介绍为主；只有篇幅、用途或秘密/时期隔离确有必要时才拆分。人物介绍的完整性不代表其中所有内容都能发送给每个NPC。

## 事实与本局状态

- 只依据实际读到的原文。清楚区分叙述事实、人物说法、传闻、误解和整理者推断；注明版本与原文范围。缺页、缺章或未读后文不能写成“原著没有”或已知结局。
- 原著资料描述作品基准；玩家造成的变化不回写成原著。原著未来也不等于本局已经发生。
- “玩家说了/尝试了”“某人听见了”“某人相信了”“事情实际发生了”“其他人获知了”是不同事实。正式本局状态只能沿用项目已确认的状态存储和总控核准流程；世界书写作不得自行创建第二份存档。
- NPC只应收到本轮任务所需且该角色实际可知的内容。秘密或后期信息不能只贴标签后仍全量发送；需要隔离时须有实际可独立投递的正文，并由请求组装流程筛选。

## 目录与系统配合

需要维护目录时，只记定位所需信息：稳定条目ID、名称、类型、别名、原文依据，以及故事条目的涉及对象和前后条目。只有确有独立调用需要时，再为内容单元记内容ID、实际条目名、时期和接收范围。目录标签本身不提供访问控制，也不表示正文已送入模型。

配合Agent/MVU/EJS时遵循三条：

1. **Agent**按现有职责处理本轮任务并返回提案；意图不等执行成功，提案不等正式状态。复用项目已有协议，不新增Agent岗位。
2. **MVU**仅在项目已采用时承载需要跨轮追踪的本局动态值；复用实际Schema和字段。不得因为世界书写作就擅自另造状态树、初始化存档或宣称字段已接入。
3. **EJS**仅在项目确有可用入口、并需按请求或状态选择资料时使用；它读取状态、筛选并输出资料，不裁定剧情、不写入状态。模板要把筛选后的结果交给实际目标Agent请求；只在主聊天存在模板，不证明独立Agent请求经过它。

若用户明确要求设计接线草案，才补充对应字段/模板/交接格式，并标明“拟定”或“待验证”；普通小说整理不要求重复生成Schema、整套JSON示例或代码。

## 编写步骤

1. 盘点实际收到并读到的作品版本、文件与范围，记下缺失。
2. 先用少量原文试写人物、规则及相邻故事段，检查格式和连续性。
3. 按授权范围分批整理；合并同名对象、沿用稳定ID，保留可回查的原文范围。
4. 检查事实身份、时间顺序、动机因果、限制例外、人物知情边界及前后条目衔接。
5. 只报告实际做过的检查；静态文档或模板检查不等于酒馆已加载、Agent已收到或状态已保存。

## 不属于本方案的事项

本方案不是酒馆导入JSON规范、可直接执行的Agent/MVU/EJS实现、整本书资料库架构或运行验收报告。目标环境、既有状态字段和请求入口未经核实时不得臆断。不得擅改正式世界书、存档、全局设置或扩展。

# 世界书编写方案

版本：v1.0
状态：用户授权保存的编写方案；尚未编写实际作品条目、实现脚本或进行酒馆实测。

## 一、目标与已确认原则

将用户提供的小说写成清楚、好读、能让 Agent 理解作品的世界书。正文写作品内容，不写系统接线说明。

- 人物完整介绍，地点写出实际风貌，势力写出组织本身，规则讲清原理与限制。
- 整本小说按原著顺序拆成许多连续故事条目，前后衔接，不要求每条独立收尾。
- 事件融入故事正文，不设独立事件条目。
- 人物不单列“原著阶段变化表”和“关联故事表”。重要变化在经历、能力等正文中自然说明。
- 不使用此前35类模板，不把同人资料库的管理格式强加给世界书。
- 一人、一地点、一势力以一份完整介绍为主；只有篇幅、独立用途或秘密隔离确有需要时才进一步拆分。
- 栏目用于帮助写清内容，不是必须填满的表。原著未交代的内容不编造；简短对象可以合并成自然段。
- 脚本按稳定ID主动读取为主，SillyTavern原生关键词辅助正文生成。准确接口待核验。
- 原著世界书与本局存档分开。玩家改变剧情，不回头把原著条目改成玩家的故事。

## 二、条目正文格式

### 1. 人物

```text
【人物：姓名】

简介：
人物的身份、来历、在作品中的主要地位。

外貌：
长相、体态、衣着和有辨识度的特征。

性格：
主要性格、处事方式、重视什么、厌恶什么。
结合原著表现写清，不堆形容词，不把倾向写成绝对行为。

经历：
按先后顺序简述重要经历，以及这些经历怎样影响了他。
只保留认识这个人物所需的内容，不复述全部剧情。

能力：
主要实力、擅长的能力、重要物品及明确限制。
前后有明显变化时，在这里说明发生于何时，不能混为同时具备。

关系：
与重要人物是什么关系，为什么形成这种关系。
存在前后变化时，用文字讲清。
```

人物介绍是作者完整阅读入口，不等于所有内容都能原样发给NPC。后期经历、秘密、其他人的内心不能自动成为该人物的本局知识。

### 2. 原著故事线

整本书的组织：

```text
原著故事线
├─ 001〈本段名称〉
├─ 002〈本段名称〉
├─ 003〈本段名称〉
└─ ……按原著顺序持续拆解到全书结束
```

每条正文：

```text
【原著故事线·001：<本段名称>】

原著范围：
<对应章节或原文范围，方便回查。>

承接：
<简短说明前文留下的处境，以及本段开始时正在发生什么。
首条直接写故事起点。>

正文：
<按原著顺序连续叙述本段剧情。
写清人物为什么行动，做了什么，说出了什么重要信息，
其他人物如何回应，事情怎样发展和转折。
多件事件自然串在正文里，不拆成事件清单。
保留关键动机、对话含义和因果，不只写几句剧情摘要。>

接续：
<写到本段停止时，事情推进到了哪里，
哪些行动、冲突或问题仍在继续。
不补写尚未发生的结果。>

上一条：<编号与名称；首条无>
下一条：<编号与名称；末条无>
```

拆分规则：

- 按场景转换、时间跳转、叙事重心变化或实际篇幅需要分条。
- 不规定一章一条，不规定一个事件一条。同一场冲突可以连续写几条。
- 不设每条必填的“故事结局”。原著确有收场时，自然写入正文。
- 保留支线、场外重要发展与人物动机，不只串主角的行动。
- 不改变原著叙述中的揭示关系；回忆、倒叙或同时发生的不同线索须写清时间关系。
- 连续条目不能有因果断层，也不大段重复上一条内容。
- 只写原著实际内容，不添加玩家分支、猜想结局或自创事件。
- 顺序编号表示原著阅读顺序，不是本局必须执行的游戏步骤。

### 3. 地点

```text
【地点：名称】

概况：
这是什么地方，位于哪里，规模如何，在作品中有什么地位。

环境与风貌：
地形、气候、建筑、景观，以及最有辨识度的环境特征。

内部布局：
主要区域、建筑、设施，各部分的位置和用途。

当地生活：
什么人在这里生活，平时有什么活动，
当地繁华或荒凉到什么程度，有什么风俗与氛围。

特色与资源：
这里特有的事物、产物、设施或吸引人前来的原因。

出入与危险：
如何到达，出入有什么要求，有哪些明确危险或禁忌。
```

正文首先让人看懂地方本身，不用关联ID和状态读取清单代替地点描写。

### 4. 势力

```text
【势力：名称】

概况：
势力的性质、来历、地位和主要活动范围。

宗旨与作风：
追求什么，重视什么，平时怎样对待成员与外人。

组织构成：
由谁领导，主要职位或分支怎样组成，
重要成员分别承担什么职责。

实力与根基：
主要强者、传承、产业、资源和立足之本。

内部生活：
成员如何加入、学习、晋升，内部有什么规矩和矛盾。

对外关系：
与主要势力的合作、依附、竞争或仇怨，以及形成原因。

重要历史：
建立、兴盛、衰落或重大变故的简要经过。
```

### 5. 世界规则或修炼体系

```text
【体系：名称】

基本原理：
这套体系是什么，力量从哪里来，如何运行。

体系构成：
有哪些类别或等级，它们之间有什么区别。

学习与成长：
如何入门、修炼、提升，需要哪些条件与资源。

实际表现：
不同层次能做到什么，对身体、生活或战斗有什么影响。

限制与例外：
明确的瓶颈、代价、禁忌和特殊情况。
```

非修炼类世界规则沿用“原理、适用范围、表现、条件与例外”写清，不强加等级结构。

### 6. 功法、技能或特殊能力

```text
【能力：名称】

介绍：
能力的来历、类别和主要特点。

作用：
能产生什么效果，使用时有什么表现。

使用：
怎样掌握和使用，需要什么条件。

代价与限制：
消耗什么，不能做到什么，有哪些风险或克制关系。
```

### 7. 物品、材料或配方

```text
【名称】

介绍：
是什么，外观与主要特征是什么。

用途：
能用来做什么，有什么具体效果。

使用方法：
怎样使用、加工或制作，需要哪些条件。

获取：
原著明确提到的产地、来源或取得方式。

限制：
使用代价、风险、保存要求或其他注意事项。
```

## 三、从小说到正文的编写方法

1. 检查实际提供的小说文件、版本、章节范围与缺失；保留原文，不补造缺章。
2. 按原著阅读顺序分批处理，保持全书故事连续性；记录已经处理和未处理的范围。
3. 将分散的人物、地点、势力和规则信息合并到对应介绍中，别名归到同一对象。
4. 按上述格式编写连续故事条目，不先制造大量独立事件档案。
5. 后文补充前文时，更新相关介绍并明确时间关系；人物的误解、传闻与客观事实分开写。
6. 正文以整理后的自然语言为主，必要证据留在维护信息中。不整章复制，也不为了省篇幅删掉因果、条件和例外。
7. 先用少量代表性原文试写人物、地点、规则及相邻故事条目，检查是否清楚，再在实际授权范围内分批扩大。

不要求先建成一整套同人资料库才能编写。只保留回查原文、合并同名对象和续写所需的轻量记录，不另造繁复的资料卡体系。

## 四、正文外的轻量目录

以下是项目维护格式，不是已验证的酒馆导入JSON。它用于定位内容，不挤进作品正文。

普通条目：

```yaml
条目ID: character-001
名称: <人物名称>
类型: 人物
别名: []
原文依据: <版本及相关章节或位置>
```

故事条目：

```yaml
条目ID: story-023
名称: <本段名称>
类型: 原著故事线
涉及人物: [人物ID]
涉及地点: [地点ID]
涉及势力: [势力ID]
原著范围: <版本及章节范围>
上一条: story-022
下一条: story-024
```

仅在需要时补充适用时期、受限内容位置、必要依赖或未知项，不要求每条填写一大张管理表。条目改名不随意更换ID；依赖链接本身不代表相关正文已进入模型请求。

## 五、配合Agent系统

### 1. 总体交接

```text
玩家输入
→ 总控判断任务
→ 脚本读取相关世界书内容与本局状态
→ 按接收者、实际知情和任务范围筛选
→ 相关Agent处理并返回提案
→ 检查本轮候选结果
→ 主生成根据核准结果写正文
→ 总控协调外部存储正式保存
```

不是每轮全调用，不把整本世界书发给每个Agent。沿用[流程方案.md](<流程方案.md>)的提交、异常处理与防循环边界。

### 2. 各模块读取范围

| 使用者 | 世界书内容 | 用途 |
| --- | --- | --- |
| 总控 | 轻量目录，必要时读相关说明 | 定位本轮对象和材料，不默认通读全库 |
| 原著资料 | 问题相关条目和原文依据 | 回答原著怎么写，必要时回查原文 |
| NPC决策 | 人物介绍中适用且允许读取的部分、相关地点与社会信息 | 结合本局知情、目标、关系形成意图 |
| 行动结算 | 能力、物品、体系及地点限制 | 结合当前资源和状态检查条件与直接结果 |
| 玩家影响与世界演变 | 相关原著故事、人物与势力内容 | 判断被改变的前提及不能照搬的后续 |
| 世界运转 | 地点、势力、规则和必要原著背景 | 结合本局时间与既有计划推进过程 |
| 主生成 | 当前场景、可见人物等必要描写内容 | 根据核准结果写正文，不重新裁定 |

### 3. 原著故事的使用

- 本轮涉及story-023时，优先读取该条；需要起因再补022，需要核对原著后续再补024，不机械加载固定邻居数量。
- 不因过去一个回合就自动读下一条，不用单一剧情游标强迫所有支线同步前进。
- 玩家可能停留、跳过、绕开或改变某段故事；原著顺序不变，本局实际进展另存。
- 原著未来只供相关后台任务参考，不等于本局已经发生，也不直接交给NPC作为知识。
- 原著资料模块不自行创造玩家分支；本局变化交给已有决策、结算、世界演变和运转流程。

### 4. 人物完整性与信息隔离

- 作者可以读完整人物介绍；NPC模型只接收当前适用的部分。
- 原著叙述揭示某秘密，不等于本局角色已获知；提到名字也不等于人物在场。
- 后期能力、关系、经历必须有可辨认的时间说明，不能作为前期当前状态发送。
- 筛选应在发送前完成，不能把秘密全部交给NPC再要求它假装不知道。
- 不能可靠筛开的受限段落，可以单独保存或暂不发送；不因此把所有普通内容都拆碎。
- 同一完整人物模型处理多个NPC时，必须核验信息隔离能力，不能仅靠标签声称隔离成功。

### 5. 两种加载方式

主路径：总控确定对象和任务，脚本按稳定ID读取，经范围筛选后加入对应模型请求。

辅助路径：原生关键词用于主生成需要的普通背景。人物秘密、后期真相和整段未来故事不应仅凭名字命中就全量进入正文请求。

- 同一资料经两条路径进入时，需要按内容身份去重；不能只假定酒馆会自动去重。
- 未确认的读取接口、模板处理与请求拼接能力均保留待验证，不在此方案中编造API。
- 按需使用少量常驻基础说明，不依靠扩大关键词扫描或递归触发补救资料缺失。
- 后续配置按目标格式核验；本轮不改酒馆全局配置、不安装扩展。

### 6. 本局状态的边界

当前时间、位置、伤势、资源、关系、知情、计划与剧情偏离来自外部状态存储，不在固定世界书里维护第二份。

原著中的对应信息仍可写入介绍，只需明确是原著基准；本局发生改变后，处理当前行动使用本局正式状态。状态缺失时报告缺失，不悄悄拿原著后期结果当存档值。

## 六、检查标准

### 编写检查

- 单读人物介绍能否看懂这个人，而不必拼七八份条目？
- 地点、势力是否有具体内容，而不是关联清单？
- 相邻故事条目是否连续，动机、反应、转折和因果是否完整？
- 是否取消独立事件条目及每条强制结局？
- 能力与物品是否保留条件、代价、限制和例外？
- 是否区分原著事实、传闻、人物误解与整理者推断？
- 是否能回查原文，且没有凭熟悉作品补造内容？

### 实现后才执行的运行检查

- 脚本能否读取正确条目，内容是否实际进入目标Agent请求？
- 不提完整名字、使用别名或持续同一场景时，必要资料是否仍可获得？
- NPC是否收到未来内容或未获知秘密？
- 关键词与脚本是否重复注入？预算不足是否保留必要条件并明确报缺？
- 本局偏离原著后是否仍被强行推进原著下一条？
- 切换会话或分支后是否读取正确状态？

以上运行检查均未执行。文档保存不代表脚本、扩展、数据库或SillyTavern已经具备这些能力。

## 七、方案关系与下一步

本方案替代此前35类条目、独立事件档案、人物阶段变化表与关联故事表，也替代[底层需求方案.md](<底层需求方案.md>)第五、六节提出的九板块讨论路线。早期文档保留作历史，世界书编写以本方案和用户后续明确修改为准。

下一步由用户选择继续讨论其他底层，或提供小说后授权小样试写。本次不开始小说整理、世界书导出、脚本实现、插件安装、付费调用或发布。

编写依据：用户逐项确认的正文格式与Agent配合方式。工具参考仅用于来源核对、写入边界与运行证据要求，不替代用户的组织方式。已读取A0及世界书编写、加载参考；Library参考快照2026-08-18。具体作品、目标版本、扩展、存储与读取API仍待实际任务核验。唯一续接入口为[NEXT.md](<NEXT.md>)。
